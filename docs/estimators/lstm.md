# lstm
- Source: our own implementation (`estimators/lstm/predict.py`): a one-layer PyTorch LSTM (32 units) with a linear head, trained on 20-day windows of three features per day (close-to-close return, high-low range over close, candle body over open), pooled across all assets, predicting the next close-to-close return. Not a third-party model.
- Licence: own code. Depends on PyTorch (BSD-3-Clause), pinned `torch==2.8.0` (CPU wheel) in `estimators/lstm/requirements.txt`, the version already in the repo `.venv` and shared with Kronos, TimesFM and Chronos. Installing it changes nothing; `pip check` is clean.
- Original code or reimplementation: own code, registry `kind: ml`, `original_code: False`. Not pretrained, so the optimistic-backtest warning for pretrained models does not apply.
- Installs on a clean GitHub runner: yes, CPU only, no weights, no downloads, no `setup` step.
- Training scheme (the weekly retrain, without a model file): the brief's design cached a model file and reused it for seven days. That cannot work here, because the workflow cache is keyed per estimator, written once and never re-saved, and a one-year replay in a single job would have no way to know what a cached file had seen. Instead the model for any day is a pure function of the data: it is trained inside `predict` on candles dated on or before the Monday of that day's week (`_boundary`), pooled across every asset in `history`, and applied to the latest 20 candles of each asset. The boundary is never later than the newest candle given to `predict`, and the runner already cuts `history` to candles before the run date, so the model cannot see the future. It is kept only in memory (keyed by boundary and a hash of the training data) so the 5 to 7 days of one week in a backfill share one training run. A live run on a Wednesday trains on exactly what Monday's run would have, so live and backfill agree and nothing is saved between runs.
- Determinism: fixed torch seed and a seeded shuffle generator, `torch.set_num_threads(1)` and `use_deterministic_algorithms(True)` during training (both restored afterwards). Training twice from scratch gives bit-identical predictions (test), and the contract test passes.
- No look-ahead, proven by tests (`tests/test_lstm.py`): (1) the trained weights are identical when every candle after the weekly boundary is replaced by different values; (2) running the real `run_estimator_day` on a price history whose candles from the run date onward are halved produces exactly the same stored predictions; (3) the model is reused within a week and retrained in the next.
- Spike result (this machine, 21 assets, about 43,000 candles, 1 thread): one training run about 27 s on the full 2019 to 2026 history, a predict on a day with the model already in memory about 0.3 s. A 30 day replay (stride 1, scratch directory) took 147 s including five weekly trainings, 0 failed days, `scripts/verify_data.py` passed. Projected: daily run about 30 s (one training), one-year stride 1 backfill about 52 trainings plus 365 cheap days, roughly 25 to 30 min locally and perhaps an hour on a 2 CPU runner, inside the 340 minute backfill budget and far inside the 45 minute daily timeout. No `backfill_stride` is needed (default 1).
- Local verification: 30 day replay in a scratch directory, 0 failed days, `verify_data.py` passed. No backtest data is committed; the full replay is meant to run in the cloud backfill workflow.
- Caveat: a tiny model trained for 8 epochs on about 40,000 noisy windows will most likely learn little beyond a mean; expect it to sit near the controls. It is here as a plain neural baseline. Floating-point results can differ slightly across CPUs and torch builds, so a regenerated backtest may differ in the last digits; committed predictions are kept by the keep-existing rule.
- Decision: include (stride 1), because it is cheap, fully deterministic, leak-free by construction and needs no cache, files or network.
