# kronos
- Source: Kronos, "A Foundation Model for the Language of Financial Markets" (https://github.com/shiyu-coder/Kronos, paper arXiv 2508.02739). Pinned to commit `67b630e67f6a18c9e9be918d9b4337c960db1e9a` (2026-04-13). The repository has no `setup.py` or `pyproject.toml`, so it cannot be a pip requirement. Instead `estimators/kronos/fetch_assets.py` downloads its three `model/*.py` files at that commit into `data/cache/kronos_src` (git-ignored, never copied into this repo) and refuses any file whose sha256 differs from the pinned value.
- Licence, code: MIT (`gh api repos/shiyu-coder/Kronos/license`, SPDX `MIT`). Licence, weights: MIT, stated in the model-card metadata of both Hugging Face repos (`license: mit`). Both allow this use.
- Weights (official org `NeoQuasar`, linked from the Kronos README): `NeoQuasar/Kronos-small` revision `901c26c1332695a2a8f243eb2f37243a37bea320` (`model.safetensors`, 98,980,656 bytes, 24.7M parameters) and `NeoQuasar/Kronos-Tokenizer-base` revision `0e0117387f39004a9016484a186a908917e22426` (`model.safetensors`, 15,842,368 bytes). About 115 MB in total. The smaller Kronos-mini needs a different tokenizer and was not used.
- Original code or reimplementation: original third-party model wrapped by our own `ClosesForecaster` subclass. Registry `kind: pretrained`, `original_code: True`.
- Installs on a clean GitHub runner: yes. `pip install -r estimators/kronos/requirements.txt` (CPU torch 2.8.0 from the PyTorch CPU index, einops, huggingface_hub, safetensors, tqdm, all pinned), then `python -m bench.cli setup --estimator kronos` downloads the pinned source and weights into `data/cache`. `predict` never touches the network: it loads from those local directories (symlink-free `local_dir`, which also works on Windows) and raises ImportError if they are missing. Kronos's own `requirements.txt` pins pandas 2.2.2; we do not install it that way and it runs with pandas 2.3.3. The package is called `model`, a generic top-level name; it is put first on `sys.path` only for this estimator.
- What the model does: Kronos tokenises OHLCV candles into hierarchical discrete tokens and an autoregressive transformer generates the next candles. We feed the last 400 daily candles (open, high, low, close, volume), generate 5 business days, and use close 1 as `expected_return` (relative to the last close) with all 5 closes stored as the path.
- Determinism: the library only samples (`torch.multinomial`). We call it with `top_k=1, top_p=1.0, sample_count=1`, which keeps only the single most likely token at each step (greedy), and also `torch.manual_seed(0)` before every call. Three consecutive predictions over six real assets were identical, and the contract test (which compares two calls) passes.
- Reproducibility caveat: greedy decoding is deterministic on one machine and thread count, but floating-point results can differ slightly across CPUs, torch builds and thread counts, so a backtest regenerated elsewhere may differ in the last digits or, rarely, flip a trade. Committed predictions are kept by the keep-existing rule and are not recomputed. Source and weights are sha256-verified at setup and before every load, and the workflows run predict with `HF_HUB_OFFLINE=1`.
- Spike result (`scripts/spike_estimator.py kronos`, 16 CPU Windows machine, 4 torch threads): model load about 3 s once; first measurement 3.8 s per asset including load; steady state 5 to 6 s per asset when predicting alone, but a replay measured end to end (30-day window, stride 5, 7 prediction days, 21 assets) took 285 s, which is about 2 s per asset-day. The spike script's projection of 8.1 h for stride 1 is the pessimistic upper bound.
- Projected cost: daily run for 21 assets about 1 to 2 minutes of compute plus about 1 minute for install and weight download (cached afterwards), against the 45 minute timeout. Backfill at stride 1 was projected at 4 h locally and 8 h on a runner, but measured in the cloud (stride 3 replay): 34.7 minutes, so stride 1 is about 105 minutes, well under the 340 minute job limit.
- Local verification: a 30-day replay in a scratch directory (stride 5, 7 prediction days) ran with 0 failed days and `scripts/verify_data.py` passed. No backtest data is committed; the full replay is meant to run in the cloud backfill workflow.
- Caveat: the backtest may be optimistic. Kronos was pretrained on data from over 45 exchanges and its training period is not guaranteed to end before the replayed year, so the model may have seen these prices (or highly correlated ones). Only the daily live predictions, made after the model was published, are a fair out-of-sample test.
- Decision: include with backfill_stride 1 (changed from 3 after the cloud measurement, so its backtest is comparable with the other accounts; the registry holds the stride), because licences (code and weights, both MIT) allow it, it installs and runs on CPU, is deterministic and passes the contract test, and the daily cost is small.
