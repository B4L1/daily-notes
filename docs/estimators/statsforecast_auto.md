# statsforecast_auto
- Source: Nixtla `statsforecast` (https://github.com/Nixtla/statsforecast), PyPI release pinned to `statsforecast==2.1.1` in `estimators/statsforecast_auto/requirements.txt`. Depended on by reference; none of its code is copied here.
- Licence: Apache-2.0 (confirmed with `gh api repos/Nixtla/statsforecast/license`, SPDX `Apache-2.0`), which allows use and redistribution as a dependency.
- Original code or reimplementation: original third-party model (`AutoETS`), wrapped by our own thin `ClosesForecaster` subclass. Registry `original_code: True`, `kind: ml`. The folder is `statsforecast_auto` so it does not shadow the `statsforecast` package import.
- Installs on a clean GitHub runner: yes, `pip install statsforecast==2.1.1` from PyPI (wheels for numba, coreforecast, statsmodels; no weights, no network at predict time). Installing it into the local venv downgraded pandas 3.0.6 to 2.3.3 (statsforecast pins pandas < 3); the repo only requires `pandas>=2.2`, so the runner is unaffected, and all 154 tests pass on 2.3.3.
- What the model does: for each asset it fits `AutoETS(season_length=1)` (exponential smoothing with automatic selection of error, trend and damping by AICc) to the last 256 daily closes and forecasts 5 closes. `expected_return` is `forecast[0] / last_close - 1`, and the 5 closes are stored as the path. Fitted from scratch on each call, so it is deterministic and needs no cache.
- Spike result (`scripts/spike_estimator.py`, 2 assets, cold): 2.3 to 3.8 s per asset, but that is dominated by numba JIT on the first call. Steady state, same process: about 0.025 s per asset (0.5 s for all 21 assets), so about 0.5 s per day for all assets. The first call in a fresh process costs about 20 s once. Measured backfill in a scratch directory: 60 days in 73 s, about 1.1 s per day, so a 365-day replay is about 7 minutes of compute. Projected daily run: under 1 minute including start-up.
- Caveat on timing: the committed one-year backfill ran on this Windows machine in 217 minutes wall clock. Re-timing afterwards showed 60 days in 73 s and byte-identical predictions for a spot-checked day, so the long wall time looks like a stall on the local machine (other work, power management) and not the cost of the model. If a cloud backfill is unexpectedly slow, set `backfill_stride`; even at the pessimistic 217 minutes it is inside the 340 minute job limit.
- Backtest result (365 days to 2026-10-07, 364 equity rows, cost model of the bench): final equity 9786.6 from 10000, that is -2.1%. Traded on 251 of 364 days. Controls over the same window: random coin -3.2%, tomorrow = today -5.4%, always long -25.6%. The estimator is slightly ahead of the random control, but a one-year difference of about one percentage point on a single path is well inside what luck can produce; it should be read as no demonstrated edge. AutoETS on a near random walk mostly forecasts a flat line plus a small damped drift, so its signal is weak by construction (SPY forecast was flat to 6 decimals in the spike).
- Decision: include as is (backfill_stride 1), because it installs cleanly, is deterministic, passes the contract test, and is cheap. It serves as a classical statistical-forecast baseline for the heavier models.
