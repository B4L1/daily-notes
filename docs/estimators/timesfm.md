# timesfm
- Source: Google Research TimesFM, "A decoder-only foundation model for time-series forecasting" (https://github.com/google-research/timesfm, paper arXiv 2310.10688). Code installed from PyPI, pinned `timesfm==2.0.2` (wheel sha256 `c7bde94beb1651e1251cdf1e9d09cf6f015e0218d038a4a836a170dc70b08071`). Its README says the package supports the 2.5 model (`timesfm.TimesFM_2p5_200M_torch`, PyTorch backend, `pip install timesfm[torch]`).
- Licence, code: Apache-2.0 (`gh api repos/google-research/timesfm/license`, SPDX `Apache-2.0`; PyPI metadata also Apache-2.0).
- Licence, weights: the model used is the 2.5 200M checkpoint, official org `google`, repo `google/timesfm-2.5-200m-pytorch`, model card metadata `license: apache-2.0` (https://huggingface.co/google/timesfm-2.5-200m-pytorch). The README states that weights up to 2.5 remain Apache-2.0. **TimesFM 3.0 weights (`google/timesfm-3.0-pytorch`) are under a separate non-commercial, non-production licence (`timesfm-non-commercial-license-v1.0`) and are deliberately NOT used.** Do not upgrade the checkpoint to 3.0 without re-reading that licence.
- Weights: revision `1d952420fba87f3c6dee4f240de0f1a0fbc790e3`, `model.safetensors` 925,181,104 bytes (about 925 MB, 200M parameters) plus `config.json` (475 bytes). sha256 of `model.safetensors` is hardcoded in `estimators/timesfm/fetch_assets.py` and checked at setup and before every load. Stored in `data/cache/timesfm_weights` (git-ignored, CI-cached). Only the official `google` org is contacted, and only by `python -m bench.cli setup --estimator timesfm`.
- Original code or reimplementation: original third-party model wrapped by our own `ClosesForecaster` subclass. Registry `kind: pretrained`, `original_code: True`.
- Installs on a clean GitHub runner: yes, CPU only. `pip install -r estimators/timesfm/requirements.txt` (timesfm 2.0.2 with CPU torch 2.8.0 from the PyTorch CPU index, huggingface_hub 0.33.1, safetensors 0.6.2, numpy), then `setup` fetches the weights. Same torch, huggingface_hub and safetensors pins as Kronos, so the two estimators coexist in one environment. In the repo `.venv` the only side effects were new pure-python packages (inquirerpy 0.3.4, pfzy 0.3.4, prompt_toolkit 3.0.53, wcwidth 0.9.2, from timesfm's `huggingface_hub[cli]` extra); torch, numpy, pandas and the rest did not change. `predict` never touches the network: it loads from the local directory with `local_files_only=True` and `HF_HUB_OFFLINE=1`, and raises ImportError if the weights are missing or altered. The workflows already run predict and backfill with `HF_HUB_OFFLINE=1` and cache `data/cache`, so no workflow change was needed.
- What the model does: a decoder-only transformer pretrained on a large mix of time series (GiftEvalPretrain, Wikimedia pageviews, Google Trends, synthetic data; per its model card). We feed the last 512 closes of one asset, take the 5-step point forecast (`max_horizon=8`, input normalisation, flip invariance, quantile crossing fix, as in the README), use close 1 relative to the last close as `expected_return` and store all 5 closes as the path. The model only sees closes (no volume, no other candle fields).
- Determinism: the point forecast involves no sampling. Three consecutive passes over six real assets returned exactly equal predictions, and the contract test (two calls) passes.
- Spike result (`scripts/spike_estimator.py timesfm`, 16 CPU Windows machine, 4 torch threads): model load 2 to 16 s once, then 0.9 s per asset-day steady state (the script's 1.0 s per asset includes load). The script's projections are 0.3 min for a 21 asset daily run and 2.0 h for a stride 1 one-year backfill. End to end, a 30 day replay (stride 2, 15 prediction days, 21 assets, scratch directory) took 178 s with 0 failed days, which is about 0.57 s per asset-day including bench overhead.
- Projected cost: daily run about 1 to 2 minutes of compute plus install (torch) and a one-time 925 MB weight download (cached afterwards), far inside the 45 minute timeout. Backfill at stride 1 was projected at 3 to 6 h on a runner, but measured in the cloud (stride 2 replay): 11.4 minutes, so stride 1 is about 23 minutes, far under the 340 minute job limit.
- Local verification: 30 day replay in a scratch directory, 0 failed days, `scripts/verify_data.py` passed. No backtest data is committed; the full replay is meant to run in the cloud backfill workflow.
- Caveat: the backtest may be optimistic. The training data is mostly non-financial and ends in 2023 per its card, but the card does not list every source in GiftEvalPretrain and the replayed year is recent, so leakage cannot be excluded outright; the model also may have seen closely related series. Only the daily live predictions are a fair out-of-sample test. Floating-point results can differ slightly across CPUs and thread counts, so a regenerated backtest may differ in the last digits; committed predictions are kept by the keep-existing rule.
- Decision: include with backfill_stride 1 (changed from 2 after the cloud measurement, so its backtest is comparable with the other accounts; the registry holds the stride), because the code (Apache-2.0) and the 2.5 weights (Apache-2.0) allow it, it installs and runs on CPU, is deterministic and passes the contract test, and the daily cost is small. The 3.0 checkpoint was excluded because of its non-commercial licence.
